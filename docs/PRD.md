## 1. 프로젝트 개요

회사 내부에서 발생하는 **인력 · 거래처 · 프로젝트** 관련 정보를 통합 관리하는 자체 업무관리 시스템이다.

회사의 주요 정보를 하나의 시스템에서 관리하고, 각 정보 간의 관계를 연결하여
**특정 인력 · 거래처 · 프로젝트를 기준으로 관련 정보를 한 번에 확인할 수 있는 환경**을 구축한다.

특정 인력이 퇴사하거나 담당 업무가 변경되는 경우에도 그 인력이 담당했거나 참여했던
프로젝트와 업무를 확인할 수 있도록 하여, **업무 공백을 최소화하고 원활한 인수인계가 가능하도록 하는 것**이 주요 목적이다.

## 3. 시스템 구조

```
계정 및 권한
    │
    ▼
인사관리
    │
    ├───────────────────────┐
    ▼                       ▼
프로젝트 관리 <───────> 거래처 관리
```

### 주요 관계

**인사관리 ↔ 프로젝트관리** (N:M)
- 하나의 인력은 여러 프로젝트에 참여할 수 있다.
- 하나의 프로젝트에는 여러 인력이 참여할 수 있다.
- 프로젝트에서 인력별 담당 역할과 투입 정보를 확인할 수 있다.
- 인력에서도 현재 참여 중인 프로젝트와 과거 참여 프로젝트를 확인할 수 있다.

**거래처관리 ↔ 프로젝트관리** (1:N)
- 하나의 거래처는 여러 프로젝트를 진행할 수 있다.
- 하나의 프로젝트는 하나의 거래처에 귀속된다.
- 거래처에서 관련 프로젝트를, 프로젝트에서 거래처 정보를 확인할 수 있다.

## 4. 도메인 정의

### 4-1. 권한 및 계정

#### 권한 구조

| 권한 | 코드 | 설명 | 특징 |
| --- | --- | --- | --- |
| 마스터 | `MASTER` | 개발 시 활용 목적 | 전체 접근 |
| 정직원 | `EMPLOYEE` | 회사 내부 정규 인력 | 모든 내부 기능 접근 · 입사일/퇴사일 존재 · 프로젝트별 외주비 입력 안 함 |
| 용역 | `CONTRACTOR` | 외부 인력 (프리랜서/외주) | 급여 개념 없음 · 프로젝트별 계약 금액 관리 · 퇴사일 대신 "참여 종료일" |

> 추후 직급 개념 도입 시 세부 권한을 분리하고, 급여관리 개념을 추가한다.

#### 계정 생성

관리자가 인사관리에서 새로운 인력을 등록하면 **해당 인력의 계정이 함께 생성된다.**
별도의 「계정 생성」 메뉴는 제공하지 않는다.

```
인사관리 → 인력 등록 → 인력 유형 선택(정직원 / 용역)
        → 필수 인력정보 입력 → 계정 생성(아이디 직접 입력 / 초기 비밀번호 0000)
        → 인력 유형에 따른 권한 자동 적용
```

- 인력 등록을 **최종 완료하는 시점**에 계정을 생성한다.
- 인력정보 입력 중 취소하거나 등록에 실패한 경우 계정을 생성하지 않는다. (단일 트랜잭션)
- 비밀번호 변경 · 찾기는 v1.0 범위 외.

#### 계정 상태

| 상태 | 코드 | 설명 | 조건 |
| --- | --- | --- | --- |
| 활성 | `ACTIVE` | 로그인 및 시스템 이용 가능 | - |
| 비활성 | `INACTIVE` | 로그인 불가 | 정직원: 퇴사 시 / 용역: 비활성화 시 |

#### 기타 원칙

1. **용역 → 정직원 권한 변경 불가.** 정직원 채용 시 새로운 계정을 생성한다.
   (추후 근태 · 휴가 · 급여 파트에서 개발적 오류 가능성이 높고 노무적으로도 옳지 않음)
2. **계정 삭제 불가.** 과거 프로젝트 및 업무 연관성에 영향을 준다.

#### 계정과 인력의 관계

계정과 인력정보는 분리하여 관리하되 반드시 연결한다.

- 하나의 인력은 **하나의 계정만** 가질 수 있다.
- 하나의 계정은 **반드시 하나의 인력에** 연결되어야 한다.
- 계정 단독 존재 및 1인 다계정은 허용하지 않는다. (`account.person_id` UNIQUE)

### 4-2. 인사관리

> `용역` 접근 불가

#### 인사관리 화면

- **검색**: 이름, 전화번호
- **필터**: 전체 / 재직 / 퇴사
- **리스트 항목**: 이름, 전화번호, 고용형태, 직무, 재직여부, 입사일, 퇴사일
- **페이지네이션**: 한 화면 12명

재직여부는 `재직` / `퇴사` 두 가지이며, 용역의 비활성화도 `퇴사`로 표시한다.

#### 인사 등록

인사 데이터는 두 플로우로 나누어 입력한다.

**① 인사 등록 FLOW (계정 생성 시점)**

| 항목 | 필수 | 형식 / 제약 |
| --- | :---: | --- |
| 이름 | O | 문자열 |
| 주민등록번호 | O | 숫자 13자리 / **민감정보** |
| 고용형태 | O | 정직원 / 용역 중 택 1 |
| 입사일 | O | YYYY-MM-DD |
| 휴대전화 | O | 숫자 입력 시 자동 하이픈 (`000-0000-0000`) |
| 주소 | O | 문자열 |
| 아이디 | O | 영문+숫자 20자 이내, 특수문자 금지 |
| 이메일 | X | 이메일 형식 |

**② 인사 관리 FLOW (등록 후 상세에서 입력)**

| 항목 | 형식 / 제약 |
| --- | --- |
| 직무 | 텍스트 |
| 계약서 | PDF · 이미지 업로드 |

#### 인사 상세

**인사정보**

| 구분 | 항목 | 형식 | 제약 |
| --- | --- | --- | --- |
| 사람 정보 | 이름 | 텍스트 | View |
| | 주민번호 | `000000-0000000` | View (**마스킹**) |
| | 전화번호 | `000-0000-0000` | Edit |
| | 이메일 | 이메일 형식 | Edit |
| 근태 정보 | 입사일 / 계약시작일 | YYYY-MM-DD | View |
| | 계약형태 | 정직원 / 용역 | View |
| | 직무 | 문자열 | Edit |
| | 재직상태 | 재직 / 퇴사 | View (파생) |
| | 퇴사일 / 계약종료일 | YYYY-MM-DD | Edit — 정직원만 노출, 해당 일자 경과 시 퇴사 처리 |
| | 비활성화 | 라디오 | Edit — 용역만 노출, 비활성화 시 재직상태 퇴사 처리 |

> 주민등록번호는 암호화하여 저장하고, 응답에는 항상 마스킹된 값만 내려간다.
> 원본 복호화 API는 v1.0에서 제공하지 않는다.

**프로젝트 정보**

참여했던 프로젝트를 카드 형태로 표시한다.
표시 데이터: 프로젝트명, 시작일, 진행여부, 프로젝트 담당. 클릭 시 프로젝트 상세로 이동.

### 4-3. 거래처관리

> `용역` 접근 불가

#### 목적

거래처의 기본정보 · 담당자 · 요구사항 · 관련 프로젝트 · 계약자료를 관리한다.
거래처를 프로젝트와 연결하여 **어떤 프로젝트를 진행 중이고 과거에 무엇을 진행했는지** 확인할 수 있게 한다.
계약서 · 사업자등록증 등의 파일을 거래처 정보에 연결하여 별도 저장소를 찾지 않아도 되게 한다.

#### 구조

```
거래처관리
├── 거래처 리스트
├── 거래처 등록
└── 거래처 상세
     ├── 기본정보
     ├── 담당자
     ├── 요구사항 및 특이사항
     ├── 프로젝트
     └── 첨부문서
```

매출 · 수금 · 세금계산서는 거래처 자체의 정보라기보다 **프로젝트 및 거래 과정에서 발생하는 정보**이므로,
v1.0에서는 거래처 상세의 관련 프로젝트를 통해 확인하도록 연결한다.

#### 거래처 리스트

- **검색**: 거래처명, 대표명, 담당자명, 담당자 연락처
- **표시 데이터**: 거래처명, 사업자등록번호, 대표명, 담당자, 프로젝트 수, 진행여부, 누적 계약액

**진행여부** (프로젝트 상태로 자동 판정)

| 값 | 조건 |
| --- | --- |
| 진행 | 진행중인 프로젝트가 존재 |
| 진행완료 | 1개 이상의 프로젝트가 존재하고 모두 완료 |
| 잠재 | 프로젝트가 아직 없음 |

**누적 계약액**: 소속 프로젝트 계약금액의 총합

#### 거래처 등록

기본정보만 먼저 등록하고, 담당자 · 요구사항 · 프로젝트 · 문서는 상세에서 추가한다.

| 데이터 | 필수 | 입력 방식 |
| --- | :---: | --- |
| 거래처명 | O | 텍스트 |
| 사업자등록번호 | O | 숫자 10자리, **중복 등록 불가** |
| 대표자명 | O | 텍스트 |
| 업종 | X | 텍스트 |
| 대표전화 | X | 전화번호 |
| 사업장 주소 | X | 주소 |
| 대표 이메일 | X | 이메일 |
| 홈페이지 | X | URL |
| 거래처 설명 | X | 장문 텍스트 |

#### 거래처 상세

| 구분 | 구성 | 제약 |
| --- | --- | --- |
| 기본정보 | 거래처 정보 (거래처명 · 사업자등록번호 · 대표자명 · 업종 · 주소 · 전화 · 이메일 · 홈페이지 · 설명) | Edit |
| | 담당자 (이름 · 직책 · 전화번호 · 이메일, 여러 명 등록 가능) | Edit |
| | 진행여부 | View (파생) |
| 업무 정보 | 요구사항 및 특이사항 (텍스트 메모) | Edit |
| | 프로젝트 (프로젝트명 · 시작일 · 진행여부 · 참여자 · 계약금액 · 마감일) | View |
| | 계약 누적액 (계약금 · 수령 · 미수금) | View (파생) |
| | 계정관리 *(추후 기획)* | Edit |
| 문서 | 사업자등록증 (PDF · 이미지) | Edit |

#### 거래처 삭제

**불가.**

### 4-4. 프로젝트관리

> `용역`은 본인이 포함된 프로젝트만 확인 가능

#### 프로젝트 리스트

- **검색**: 프로젝트명, 거래처명
- **표시 데이터**: 프로젝트명, 거래처명, 계약기간, 실제 종료일, 계약금액, 진행상태, 담당자
- **페이지네이션**: 한 화면 12개

**진행상태** (파생값)

| 값 | 코드 | 조건 |
| --- | --- | --- |
| 예정 | `PLANNED` | 계약 시작일이 아직 오지 않음 |
| 진행중 | `IN_PROGRESS` | 계약 기간에 포함된 일자 |
| 완료 | `COMPLETED` | 실제 종료일이 입력됨 |

계약기간이 끝났는데 진행중인 경우 `overdue` 로 판정하여 화면에서 계약기간을 **빨간 글씨**로 표시한다.

#### 프로젝트 개설

처음 생성할 때는 최소 정보만 입력한다.

| 항목 | 필수 | 형식 / 제약 |
| --- | :---: | --- |
| 프로젝트명 | O | 텍스트 |
| 거래처 | O | 등록된 거래처 선택 |
| 계약 시작일 | O | YYYY-MM-DD |
| 계약 종료일 | O | YYYY-MM-DD (시작일 이전 불가) |
| 계약금액 | X | 숫자 (세 자리 콤마 자동) |
| 업무 담당자 | X | 등록된 정직원 선택 |

> **계약기간과 실제 프로젝트 운영기간은 별도로 관리한다.**
> 계약 종료일과 실제 종료일이 다를 수 있으므로 실제 종료일은 프로젝트 상세에서 입력한다.

개설 완료 시 프로젝트 상세 화면으로 이동한다.

#### 프로젝트 상세

**기본정보**: 프로젝트명, 거래처, 계약기간, 실제 종료일, 계약금액, 진행상태, 담당자

**프로젝트 상세내용**: 설명 및 업무 참고사항 (장문 텍스트)

**참여인력**

| 항목 | 정직원 | 용역 |
| --- | :---: | :---: |
| 참여인력 | O | O |
| 역할 | O | O |
| 용역비 | X | O |

- 정직원은 회사에서 급여를 지급하므로 프로젝트별 금액을 입력하지 않는다.
- 용역은 프로젝트별 계약으로 비용이 발생하므로 프로젝트에 용역비를 직접 입력한다.
- 용역비는 정직원(및 마스터)만 입력할 수 있다.
- **용역 본인은 타인의 용역비를 확인할 수 없다.** (본인 용역비만 조회 가능)
- 참여인력이 퇴사하거나 용역 참여가 종료되어도 **기존 프로젝트에서 삭제하지 않는다.**
  참여 이력을 유지하고 해당 인력의 현재 상태를 함께 표시한다.

**계약서**: PDF · 이미지 업로드 및 확인

#### 프로젝트 종료

실제 종료일을 입력하고 진행상태를 `완료`로 변경한다. 계약 종료일은 그대로 유지한다.

```
계약기간   6/1 ─────────── 8/31
실제 운영  6/10 ───────────── 9/5
```

#### 프로젝트 삭제

기획 미확정. **v1.0에서는 삭제를 제공하지 않는다.**

## 6. 비기능 요구사항

| 항목 | 내용 |
| --- | --- |
| 인증 | JWT — Access 30분(응답 바디) / Refresh 14일(httpOnly · SameSite 쿠키), 재발급 시 rotation |
| 비밀번호 | BCrypt 해시, 초기값 `0000` |
| 민감정보 | 주민등록번호 AES-256-GCM 암호화 저장, 응답은 항상 마스킹 |
| 페이징 | 인사 · 프로젝트 목록 12건 고정 |
| 파일 | PDF · 이미지, 단건 10MB 제한 |
| 시간대 | `Asia/Seoul` |
| 이력 | 모든 테이블 `created_at` / `updated_at` 자동 관리 |

## 7. v1.0 결정사항 요약

1. 목업의 `자사 프로젝트`처럼 거래처 없는 프로젝트가 존재할 수 있으나,
   기획서 원칙("프로젝트는 하나의 거래처에 귀속")을 따라 `client_id` 는 **NOT NULL** 로 두고
   자사도 거래처로 등록하는 것을 원칙으로 한다.
2. 주민등록번호는 암호화 저장 + 마스킹 응답. 원본 조회 API 미제공.
3. 프로젝트 · 거래처 · 계정 모두 **삭제 불가**.
4. 프로젝트 진행상태, 거래처 진행여부, 누적 계약액은 **컬럼으로 저장하지 않고 조회 시 계산**한다.
5. 수금(`received_amount`)은 프로젝트 단위로 보관하며, 거래처 계약 누적액은 이를 합산한다.
   본격적인 수금관리는 v1.n 에서 다룬다.
